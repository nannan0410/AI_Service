## 1. 问题背景

智能对话工具真实落地时，需要对接后台与底层系统数据。是否需要一个地方维护：

- **触发条件（标签 / 规则）**
- **展示字段项**

**结论：需要系统性地维护，但不建议全部塞进一个配置文件，应分层、分域维护。**

| 维度 | 示例 | 变更频率 |
|------|------|----------|
| 触发条件 | 新客标签、在园、有待出行订单（`visitDate >= 今天`） | 运营 / 产品 |
| 数据能力 | 调哪些 API、字段从哪来 | 后端 / 集成 |
| 展示字段 | 券卡片显示满减条件 | 产品 / 前端 |

---

## 2. 推荐生产架构（四层）

```
① 元数据目录（Tag / Field Catalog）
   ↓ 引用
② 场景配置（Skill / RecommendEntry / welcome_questions / welcome_templates）
   ↓ 调用
③ 数据适配层（Tool Handler + API Binding）
   ↓ 格式化
④ 展示模板（Card Schema / View Config）
```

## 2.1 Skill 场景 vs 欢迎页推荐入口

| 维度 | **Skill 场景**（`skills.json`） | **推荐入口**（`recommend_entries.json`） |
|------|--------------------------------|------------------------------------------|
| **定位** | 对话侧的**能力单元**（能做什么） | 面向游客的**运营入口**（推什么、怎么点） |
| **维护者** | **拆分**：运营维护补充关键字；技术 / 运维维护 **SKILL工具目录**、Skill 绑定工具（选自目录）、指令、启停、外部接口 | 运营 / 产品（文案、规则、优先级） |
| **核心字段** | `defaultKeywords` / 子意图 `keywords`、`customKeywords`（合成为路由用 `triggerKeywords`）、`toolBindings`（或兼容 `tools`）、`promptAddon` | `title`、`icon`、`rules`、`promptHint`、`skillId` |
| **触发方式** | 用户**发消息后**关键词匹配路由 | 欢迎页**展示 chips**，用户点击后发起对话或跳页 |
| **是否含正文** | 否，只定义调哪些 Tool | 否，只有标题与 prompt 提示语 |
| **与用户状态** | 不直接判断（路由看消息文本） | **规则引擎**按 persona / 在园 / 订单等过滤 |
| **一对多关系** | 1 个 Skill 可被多个入口引用 | 多个入口可指向同一 `skillId` |

- **Skill ≈ 实际功能**：Tool 列表、LLM 指令、Workflow。
- **推荐入口 ≈ 展示**：标题、图标、出现时机；点击发 `promptHint` 后进对话路由。

**后台菜单拆分（正式口径）：**

| 入口 | 可见范围 | 可配内容 |
|------|----------|----------|
| 对话与配置 → Skill关键词 | 运营 / 客户侧后台 | 列表（状态只读展示运维启停结果）、**补充关键字** `customKeywords`（与默认同级挂载；抽屉内其它字段只读）。**无启停** |
| 运维管理 → Skill 场景 | **仅技术人员**（不对客户开放；未来合并运维中心） | Skill **新增/编辑同一抽屉**：**绑定工具从「SKILL工具」目录下拉选择**（≤20，读写不得宽于目录）、`promptAddon`、**默认关键字**、**补充关键字（只读）**、**子意图 0～10 内嵌**（每子意图默认 + 补充只读 + 多工具，读写 ⊆ Skill）；**SkillID 新增手填、提交后只读**；操作日志占位（独立抽屉）；列表开关控制 `enabled` |
| 运维管理 → SKILL工具 | 同上 | **全局工具目录**：能力标识 + 名称 + 默认读写（≤20）；Skill / 子意图绑定只能从此选取，不可手填发明标识 |
| 运维管理 → 外部接口对接 | 同上 | 环境级 / 全局外部接口 Base URL 与凭证占位（地图 / 订单 / 天气 / LLM）；默认查看，编辑后提交 |

## 2.2 欢迎页：「推荐对话」与「快捷服务」

**命名对照（钉死）：**

| 角色 | 名称 | 数据源 |
|------|------|--------|
| 后台菜单 / 配置页 | **推荐对话** | `welcome_questions.json` |
| 游客端欢迎区区块标题 | **游游推荐**（展示名，可另配） | 同上 |
| 历史别名（勿新建） | 「为您推荐」「猜你想问」 | 同上数据，仅旧文案 |
| 后台菜单 / 配置页 | **快捷服务** | `recommend_entries.json` |
| 游客端 chips 区标题 | **快捷服务** | 同上 |

| 维度 | `welcome_questions.json` | `recommend_entries.json` |
|------|--------------------------|---------------------------|
| **后台菜单名** | **推荐对话**（原「游游推荐」） | **快捷服务** |
| 展示位置 | 欢迎区推荐问题（默认 3 条 + 展开，最多 8 条）；端上区块标题目前多为 **「游游推荐」**（展示名，可与菜单名不同） | 欢迎区 **「快捷服务」** chips（最多 4 条） |
| 个性化 | 与快捷服务同一套 **规则表达式**（`rules` + `evaluateRules`）；演示账号只是 `personaId` 规则选项之一 | 同左 |
| 后台编辑 | `/config/business` → **推荐对话**；HTML 原型同名菜单 | `/config/business` → **快捷服务** |
| **优先级** | `priority` **降序**（越大越靠前；可配 `pinTop` 置顶） | 同左（无置顶）；命中后取前 `MAX_QUICK_SERVICES`（4）条 |
| **当前 Chat 页** | ✅ **已接入** | ✅ **已接入**（Phase C） |

**标题区文案**仍由 `welcome_templates.json` 按 `personaId` 提供（`title` / `subtitle` / `body`），**不含**推荐问题列表。

**Hero 当日天气 / 客流**（`WelcomeHero`）：「我是游游」上方展示天气 Mock + 随机客流一档（`scenicWeather.ts` / `scenicCrowd.ts`）。推荐对话「今天适合游玩吗」走独立 Workflow（天气 + 随机人流文案，不落通用 LLM）。

**规则求值说明：** 「演示账号」(`personaId`) 按登录账号过滤；「是否在园 / 待出行订单 / 可领新客券」等字段按该演示账号的 Mock 上下文求值（见规则预览）。后台编辑时勿在打开弹层时重置条件值；`personaId` 支持多选（存为 `in`）。

**占位符**（`welcomeTemplateVars.ts`）：`{{nickname}}`、`{{nextVisitDate}}`、`{{upcomingVisitOrderCount}}`、`{{pendingVisitSubtitle}}`。出行日当天 `pendingVisitSubtitle` = **「今日出行」**。

### 2.4.1 待出行相关规则字段（演示版摘要）

| 字段 | 计算方式 |
|------|----------|
| `hasPendingVisitOrder` | **演示：** 存在 `paid/pending` 且 `visitDate >= 今天` 的订单。**正式：** 见 §2.4.3（订单待核销 ∨ 票夹待核销） |
| `nextVisitDate` | 上述待出行集合中 **出行日最早** 的日期（正式含票夹倒查时取最早可用出行日） |
| `upcomingVisitOrderCount` | 待出行订单笔数（演示仅订单；正式票夹可另计票张数，入口布尔仍用合成字段） |

| `inPark` | **演示：** `visitorState.inPark` 写死。**正式：** 见 §2.4.2（订单已核销 ∨ 票夹已核销 ∨ GPS 围栏） |

|------|------|
| 今日推荐路线 | 有待出行 **且** 在园 |

### 2.4.2 规则字段定稿：是否在园（`inPark`）

> 与「今日有票/有订单」(`hasVisitToday`) **不是同一字段**：有今日票 ≠ 已入园；`inPark` 表示**已经进入园区游玩态**。
> 与「待出行」(`hasPendingVisitOrder`) **对偶**：待出行看 **待核销**；在园看 **已核销**（或 GPS）。同一人可先待出行、入园核销后转为在园（待出行应变 false，除非还有其它未核销票）。

#### 合成规则（产品定稿）

```
inPark = S1 ∨ S2 ∨ S3
```

任一信号为真即视为在园（推荐入口、园内 Skill 显隐用这一布尔）。后续若要做「置信度 / 强校验」（如发园内券必须闸机核销），可再拆 `inParkSource` / `inParkConfidence`，**本期入口规则只用合成布尔**。

| 信号 | 含义 | 数据来源 | 能覆盖的缺口 |
|------|------|----------|--------------|
| **S1 订单核销** | 今日有订单，且订单已核销（含可查到的 **OTA 订单**） | 订单中台：出行日=今天 + 核销状态 | 自营/已归集到账号的订单 |
| **S2 票夹核销** | 票夹内有**今日**门票/年卡，且已核销 | 按当前账号绑定的**实名游客**倒查票务（不依赖「下单账号=本人」） | OTA 下单、同行人代买、票在别人订单里但人在本人实名下 |
| **S3 GPS 围栏** | 用户已授权定位，且当前位置落在景区配置的园区范围内 | 客户端回传坐标 + 运维配置的围栏 | 无票数据、票未及时回传、仅逛未核销等弱信号 |

**注意：** `hasVisitToday`（今日有待出行订单）**不能**单独推出 `inPark`——未入园也可能有今日票。

#### 运维可配（建议运维管理）

| 配置项 | 说明 |
|--------|------|
| 园区围栏 | 每景区一套：圆心+半径 **或** 多边形顶点；坐标系与客户端约定一致（国内常见 **GCJ-02**） |
| 定位开关 | 是否启用 S3；未授权定位时 S3=false，不影响 S1/S2 |
| （可选）缓冲带 | 出入口外扩若干米，减少门口误判 |

订单/票务核销对接属接口与主数据，不在「每条服务推荐」里手写。

#### GPS 在园到底怎么判？（学习说明 + 本项目选型）

| 方式 | 原理 | 是否作本项目主依据 |
|------|------|-------------------|
| **A. 坐标 + 围栏（推荐主路径）** | 设备/小程序 `getLocation` 得到 **经纬度**（绝对坐标）→ 服务端做 **点是否在多边形/圆内**（point-in-polygon / 距离≤半径） | **✅ 正式主路径** |
| **B. 逆地理 / POI 名称** | 地图服务把坐标反查成「靠近某某 POI / 上海海洋公园」等文案 | ❌ **不单独作闸**：名称易漂、门口/停车场/相邻园区误匹配；最多作辅助日志 |
| **C. 地图 SDK「是否在某 AOI」** | 部分图商对园区有面状 AOI，本质仍是 **坐标落在官方/自建面内**，不是「返回一句公园名就算在园」 | 若图商 AOI 可靠可作围栏数据源之一，语义仍同 A |

**结论：** 「知道你在园」= **回传的经纬度落在系统为该景区配置的地理围栏内**；不是靠聊天或 POI 文案里出现公园名字。客户端只负责授权与上报坐标（及精度/时间戳）；**是否在园由服务端按运维围栏计算**（勿只信前端开关）。

演示版不做真 GPS：Persona 写死 `visitorState.inPark`（如 `demo_vip=true`）。

#### 展示 / 使用注意

| 场景 | 建议 |
|------|------|
| 快捷服务 / 推荐对话 `inPark=true` | 用合成布尔即可 |
| 园内发券、虚拟排队等 | 可用同一 `inPark`；若风控要求更严，领取时再校 S1/S2（GPS 可伪造） |
| 用户拒授权 | S3 不可用；有核销仍可在园；无核销则 `inPark=false`，不弹报错，仅少展示园内入口 |

#### 欢迎页「是否在园」自报（落地触发）

当 **无法从当日票/单与定位推断在园相关信号** 时，欢迎区可询问游客是否在园（补入口，不伪造标签）。**三条件同时满足**才展示：

1. **没有当日订单**（含 OTA/TA；当前景区、出行日=今天）  
2. **票夹没有当日票**（实名倒查；含他人下单但票面含本人）  
3. **未授权定位**（S3 不可用）

**手动标记频次：** 按账号+景区存自然日；**跨日清空**可再问，**同日最多问一次**；一旦系统能判当日票/单或定位在园，以系统信号为准。详述见 [`对话意图识别与LLM分工.md`](./对话意图识别与LLM分工.md) §1.3。

#### 演示 vs 正式

| 项 | 演示 | 正式 |
|----|------|------|
| `inPark` | `visitorState.inPark` | S1∨S2∨S3 |
| 围栏 | 无 | 运维按景区配置 |
| 票夹倒查 | 无 | 实名绑定 + 票务核销状态 |

### 2.4.3 规则字段定稿：待出行（`hasPendingVisitOrder`）

> 与「是否在园」结构相似，但看的是 **待核销 / 未入园可用票**，**不含 GPS**。  
> 规则字段名沿用演示的 `hasPendingVisitOrder`（入口配置已大量使用）；正式语义 = **订单待核销 ∨ 票夹待核销**，不单指「本人账号下单」。

#### 合成规则（产品定稿）

```
hasPendingVisitOrder = T1 ∨ T2
```

| 信号 | 含义 | 数据来源 | 能覆盖的缺口 |
|------|------|----------|--------------|
| **T1 订单待核销** | 存在仍有效、**尚未核销**的出行订单（含可查到的 **OTA 订单**） | 订单中台：待核销 + 出行日未失效（通常 `visitDate >= 今天`，以票务/订单状态为准） | 自营/已归集到账号的订单 |
| **T2 票夹待核销** | 票夹内有仍有效、**尚未核销**的门票/年卡 | 按当前账号绑定的**实名游客**倒查票务 | OTA 下单、同行人代买、票不在本人订单列表里 |

**不要**用「仅 visitDate≥今天 且 paid」代替「待核销」：正式以核销状态为准；演示暂无核销态，才用 paid/pending + visitDate 近似。

#### 与在园 / 今日出行的关系

| 字段 | 核心 | 典型用途 |
|------|------|----------|
| `hasPendingVisitOrder` | 还有票/单 **没核销** | 交通指南、帮我规划路线、查看待出行订单 |
| `inPark` | **已核销**（或 GPS 在园） | 园内路线、停车、打卡、虚拟排队 |
| `hasVisitToday` | 出行日=今天的待核销（或演示待出行订单） | 「今日出行」文案；可与在园组合 |

**互斥倾向（单人单票）：** 该票核销后 T 侧应变 false，S 侧可 true。  
**并存：** 一人多票时，可能「一张已核销在园 + 同行人票仍待核销」→ `inPark` 与 `hasPendingVisitOrder` 可同时 true（路线入口用 AND/互斥规则时注意：现行「今日路线=待出行∧在园」「规划路线=待出行∧不在园」在并存时优先展示园内入口，或后续按产品改优先级）。

#### 运维 / 对接

| 项 | 说明 |
|----|------|
| 运维配置 | 待出行**无**独立围栏项；依赖订单/票务接口与实名绑定 |
| 与在园共用 | 实名倒查、OTA 归集能力与 §2.4.2 同一套票务对接 |

#### 演示 vs 正式

| 项 | 演示 | 正式 |
|----|------|------|
| `hasPendingVisitOrder` | `paid/pending` ∧ `visitDate>=今天`（仅订单） | T1∨T2（待核销） |
| 票夹倒查 | 无 | 实名绑定 + 待核销状态 |
| OTA | Mock 订单里可写 | 订单归集 + 票夹倒查 |

### 2.4.4 规则字段定稿：景区点评 / 可开票 / 会员等级

#### 今日可景区点评（`canScenicReviewToday`）

**产品定义（现行入口）：** 当前账号在当前景区满足点评准入，且当日尚未提交过景区点评。

```
准入 = 已核销订单 ∨ 已核销票夹（演示≈completed）∨ 在园（含自报）
canScenicReviewToday = 准入 ∧ 今日未点评
```

| 项 | 口径 |
|----|------|
| 字段 | 布尔：`canScenicReviewToday`（快捷服务「服务点评」等**现行**规则） |
| 表单 | **不选订单**；可选推荐游玩项目；详见 [`景区点评优化规格.md`](./景区点评优化规格.md) |
| 发券 | 提交不发券；达标（>20 字 + ≥2 图）且分享成功后发券（日限 1 次） |

#### 可评价订单（`hasReviewableOrders`，兼容旧规则）

**产品定义：** 当前账号（当前景区范围内）存在订单满足 `status=已完成 ∧ 评价状态=未评价`（演示另加 90 天窗）。

| 项 | 口径 |
|----|------|
| 字段 | 布尔：`hasReviewableOrders`；**兼容预览**，新入口请用 `canScenicReviewToday` |
| 评价状态 | 演示枚举：`none` / `submitted`；缺省按未评价 |

#### 可开票订单（`hasInvoiceableOrders`）

**产品定义：** 当前账号（当前景区范围内）存在订单满足：

```
status = 已完成  ∧  开票状态 = 未开票
```

| 项 | 口径 |
|----|------|
| 字段 | 布尔：`hasInvoiceableOrders`（有则 true，供快捷服务「开发票」等） |
| 开票状态 | 演示枚举：`none`=未开票，`applied`=已申请，`issued`=已开具；**仅 `none` 算可开票** |
| 订单范围 | 当前登录账号可见订单；按当前景区过滤 |
| 渠道 | 正式建议：**仅允许可开票渠道**（自营等）；OTA/TA 只读订单一般不可开票——对接时在过滤层排除，不单靠状态字段 |
| 时间窗 | **产品核心不含窗口**；演示 **90 天内**（`invoiceableOrders.ts`）。正式进 **参数配置「可开票窗口(天)」**；规则字段与批量开票假页须同一窗口 |

入口显隐看布尔；提交开票时中台再校状态/窗口/渠道。

#### 会员等级（`memberLevel`）

**产品定义：** 当前登录账号的会员等级（会员主数据），非订单推导。

| 项 | 口径 |
|----|------|
| 字段 | 字符串：`memberLevel`（演示如「普通会员」「黄金会员」；来自 `memberInfo.level`） |
| 规则用法 | 相等 / 属于集合（`eq` / `in`），用于会员专属入口、权益选品等 |
| 来源 | 会员中台 / 账号资料；**不是**规则引擎自己算出来的 |
| 运维 | 等级枚举与权益绑定在会员/主数据侧；规则字段目录只读展示可用取值说明 |

与标签 `tags`（如新客、亲子）不同：等级是会员体系主属性；标签可多选、可运营打标。

#### 字段对照

| 字段 | 类型 | 一句话 |
|------|------|--------|
| `canScenicReviewToday` | boolean | 可进景区点评入口（准入 ∧ 今日未评） |
| `hasReviewableOrders` | boolean | 有已完成且未评价的订单（兼容旧规则） |
| `hasInvoiceableOrders` | boolean | 有已完成且未开票的订单 |
| `memberLevel` | string | 当前账号会员等级 |

#### 演示 vs 正式

| 项 | 演示 | 正式 |
|----|------|------|
| 可评价 / 可开票核心 | completed + none | 同左 |
| 时间窗 | 代码写死 90 天 | 参数配置可调；规则与假页一致 |
| OTA 开票 | Mock 未严格排除 | 过滤不可开票渠道 |
| 会员等级 | Persona JSON `level` | 会员中台实时等级 |

## 2.5 运行时：意图识别与对话路由

用户发消息后，**不只有 Skill 的 `triggerKeywords`**。演示版为 **Workflow 正则（代码）优先 → Skill 关键词 → LLM / 离线 Tool**。

### 2.5.1 总流程（`ChatPage.vue` → `onSend`）

> **详表与分层说明以 [`对话意图识别与LLM分工.md`](./对话意图识别与LLM分工.md) §1 为准**；本节只保留配置层对照，避免双写。

用户发消息后：Skill 关键词（可选语义补全）→ **Workflow 正则优先** → 未命中再走主对话 LLM / 离线兜底。卡片由 formatters 渲染。

> 完整对照表与「购票为何不用 LLM」说明见 [`对话意图识别与LLM分工.md`](./对话意图识别与LLM分工.md)。

```
用户输入文本
    │
    ├─① Workflow 层（代码正则，最高优先级；ChatPage 执行顺序摘要）
    │     新客领券 / 停车缴费 / 虚拟排队 / 明星介绍 / 演出场次
    │     游玩攻略（travel_guide：full / traffic / entry / in_park / recommend）
    │     购票 / 会员权益选品（member_offer） / 主动营销（餐饮零售）
    │     发票 / 打卡 / 点评 / 订单查询
    │
    ├─② 未命中 → sendChatMessage
    │     skillStore.resolveSkill(text)     // skills.json triggerKeywords
    │     → LLM + Tool Calling（或离线 fallback）
    │
    └─③ formatters → 业务卡片 / 单条消息框回复
```

**要点：** 新客领券 **无独立 Skill**，不读 `triggerKeywords`；命中 Workflow 后 **不走 LLM**；`member_offer` 优先于泛查券营销。

| 默认关键字 | 只读展示（合集） | **无子意图**：可编辑 `defaultKeywords`；**有子意图**：只读合集，编辑入口在子意图 |
| `customKeywords`（补充关键字） | ✅ 可增删（与默认同级挂载） | 只读展示；参与 0→1 / N→0 迁移 |
| `toolBindings`（绑定工具） | 只读展示 | ✅ **从「SKILL工具」目录下拉选择**（不可手填标识）；每组可覆盖 `read` / `write`（**不得宽于目录默认**）；**最多 20 组**；已选不重复；目录用尽或满 20 则禁用添加 |
| 子意图（运维抽屉） | 只读展示（运营抽屉可编各子意图补充词） | ✅ **内嵌于 Skill 新增/编辑**（不再单独入口）；**0～10（可选）**；每子意图：名称 + **默认关键字** + **补充关键字** + 多组工具（工具 ∈ Skill.`toolBindings`）；Skill 工具为只读 → 子意图锁定只读；为写入 → 默认可改写入 |
| `promptAddon` | 只读展示 | ✅ |

**关键字两级与路由合成：**

```typescript
// 存储（建议）
defaultKeywords?: string[]     // 仅当 subIntents.length === 0 时有写权限（运维）
customKeywords?: string[]      // 补充；无子意图时挂 Skill；有子意图时清空，改挂各 subIntent.customKeywords
subIntents?: SkillSubIntentConfig[]

// 派生
resolvedDefaultKeywords =
  subIntents?.length
    ? unique(flatten(subIntents.map(s => s.keywords)))
    : (defaultKeywords || [])

resolvedCustomKeywords =
  subIntents?.length
    ? unique(flatten(subIntents.map(s => s.customKeywords || [])))
    : (customKeywords || [])

// 运行时路由（兼容现有 triggerKeywords；有子意图时亦可按子意图收窄匹配）
triggerKeywords = unique([...resolvedDefaultKeywords, ...resolvedCustomKeywords])
```

**默认 / 补充关键字归属与迁移（方案 B）：**

| 规则 | 说明 |
|------|------|
| 挂载点 | 默认与补充均：有子意图 → 挂**子意图**；Skill 上默认展示为合集只读、补充仅在子意图卡片。无子意图时二者均可挂 Skill |
| 子意图可选 | **不强制**每个 Skill 都有子意图（0～10） |
| 0→1（方案 B） | **同页**创建第一个子意图时，将 Skill `defaultKeywords` **与** `customKeywords` 一并迁入该子意图，toast 提示；随后 Skill 级默认改为只读合集，Skill 级补充隐藏 |
| 再增子意图 | 不自动搬词；新子意图自填 |
| N→0 | 删光子意图后，将各子意图默认合集写回 Skill `defaultKeywords`，补充合集写回 Skill `customKeywords`（写权回到 Skill） |
| 谁维护 | 默认 → 运维可编；补充 → 运营可编、运维只读可见 |
| 双源禁止 | `subIntents.length ≥ 1` 时不得与子意图并行维护一套可写的 Skill `defaultKeywords` / `customKeywords` |

**触发关键词规则（运营后台 / 校验）：**

| 规则 | 说明 |
|------|------|
| 默认只读 | 运营抽屉展示默认关键字（锁），不可删 |
| 补充可编 | 运营维护 `customKeywords`（Skill 或子意图级）；勿与同层默认词重复 |
| 本 Skill 内唯一 | 同一关键词（默认 ∪ 补充，含各子意图）在本 Skill 内唯一，保存时报错；跨 Skill 撞词由冲突检查对照 |
| 合成路由 | 运行时仍用合并后的 `triggerKeywords`（该层默认 ∪ 补充）做包含匹配（更长优先） |

校验实现：`src/utils/skillKeywordValidation.ts`（需按两级字段与本 Skill 内唯一调整）；目录：`src/utils/skillIntentCatalog.ts`。

| 绑定券 ID | 当前新客券活动发放的券产品 ID（如 Q123 → 活动改绑 Q889） |
| 注册后可领期限 | 自注册成功起 N 天内可领（例：7 / 30） |

券产品本身另有**普通领取条件**（中台能力）：同一券 ID、同一用户限领张数等。**新客券默认：同券 ID 每用户限领 1 张。**

#### 11.4.2 两层互斥（必须分开记）

| 层 | 记什么 | 换绑券 ID 后行为 |
|----|--------|------------------|
| **A. 新客券活动资格（一次性）** | 用户是否已对「新客券活动」领取过 **1 次**（与当时发的是哪张券无关） | 昨天领过 Q123，今天改绑 Q889 → **仍不可领**，推荐入口也不再展示 |
| **B. 券 ID 限领** | 当前绑定券 ID 的「同 ID 限领张数」（默认 1） | 若从未换过 ID：活动已领过 ≈ 该 ID 已达上限，主动再领报错；若已换 ID：B 对 Q889 可能仍为 0，但 **A 已消耗仍拦截** |

示例：注册窗口 7 天；昨绑 Q123（15 元）已领 → 今绑 Q889（30 元）未持有该 ID → **不允许再领**（按 A，不按「Q889 是否领过」）。

#### 11.4.3 展示推荐 vs 点击领取校验（必须不同）

| 时机 | 依据 | 失败表现 |
|------|------|----------|
| **客服是否展示推荐**（快捷服务 / 推荐对话 / chip） | 仅 **活动侧预判**：新客 ∧ 窗口内 ∧ **未消耗活动一次性资格（A）** → `canClaimNewGuestCoupon=true` | **不展示**入口；不弹券报错 |
| **点击领取 / 领券意图提交** | **完整校验**：身份 + 窗口 + **A** + **B（当前券 ID 限领）** + 发券中台其它条件 | 返回明确错误（已领过活动 / 该券已达限领 / 超期 / 非新客等）；已领过可附带历史券卡 |

不要用「当前券 ID 是否已有一张」单独驱动入口显隐——换绑后会误露出「可领 Q889」入口。

#### 11.4.4 演示实现 vs 正式缺口

## 12. 智能购票场景（多轮 Workflow）

> 首次购票指引与老客购票共用 **`ticket_purchase` Skill + 多轮 Workflow**；会话状态由 `purchaseStore` 维护。

### 12.1 对话步骤

| 步骤 | 动作 | 说明 |
|------|------|------|
| 1 | 问人数 | 几人出行、是否有老人/小孩；可分步收集 |
| 2 | 问日期 | 具体日期或模糊说法（这周末、下周） |
| 3 | 解析日期 | `visitDateParser.ts`：模糊时段取距今天最近且 **≠ 当天**；**下周末/下个周末** 优先于「周末」 |
| 4 | 资格确认 | 含儿童 → 身高是否 ≤ 景区阈值；含老人 → 是否已满 N 周岁；**整批是/否卡**（可先后）；否→人数并入成人 |
| 5 | 主动营销 | 无 **可用** 新客券时 `issueCoupon(cp_prod_purchase)`（追问阶段可单独出券卡；**推荐成功时与票卡同框**，见下） |
| 6 | 推荐产品 | 可闭环 → **单条**推荐卡（单 SKU / 成人+儿童/老人购物车；有营销券时写入 `offerCoupon`，同框级联：文案→券→票）；不可闭环 → **兜底话术 + 购票列表按钮**（见 §12.5） |
| 7 | 确认下单 | 仅 `recommend` 步：点击推荐卡按钮 → `createOrderDraft`（可带 `items[]`）→ `/order/submit` |
| 8 | 下单页 | `/order/submit` 展示多行明细与汇总 → 选手实名出行人 → Mock 支付 → **`/orders?tab=1`**（待出行/已完成 Tab） |

### 12.2 选品规则（`matchPartyToProducts`）

选品前先经 `applyPartyEligibility`：身高超限儿童、未满龄老人并入 `adult`。

| 人数（有效） | 结果 | 说明 |
|------|------|------|
| 2 大 1 小 | `single` | 精确匹配家庭套票 `tkt_family`（套票单独成单，不与单品混单） |
| N 大 0 小 | `single` | 成人票 `tkt_adult` × N |
| 0 大 N 小 | `single` | 儿童票 × N |
| 3 大 1 小、1 大 1 小 等（无精确套票） | `cart` | 成人票 + 儿童票购物车合并下单（**禁止**套票与单品混单） |
| 纯老人 / 成人+老人（满龄） | `single` / `cart` | 老人票 `tkt_elderly`（演示景区）；无 SKU → `no_product` |
| 含老人且无老人票 | `no_product` | 提示无符合规则产品 → 购票列表 |

**资格阈值：** `src/mock/scenic/ticket_eligibility.json`（`childMaxHeightCm` 默认 120，`elderMinAgeYears` 默认 60）+ 业务场景页本机覆盖。

**卡片推荐标签：** `tickets.json` → `recommendLabel`；留空则不显示。套票标签如「家庭套票」；购物车标签为「单品组合」。

### 12.5 无法闭环兜底

| 分支 | 对话提示 | UI |
|------|----------|-----|
| `no_product` | 当前没有符合规则的可售产品（含老人等无法匹配） | `ticket_fallback` 卡 +「去购票列表选购」→ `/tickets` |

- **专用券：** `cp_prod_manual` 购票优享 5 元券（与停车 `cp_prod_parking` 等同为 5 元但 **券产品 ID 不同**，互不冲突）
- **识别与去重：** 券实例带 `couponProductId`；`findFallbackPurchaseCoupon()` / Mock `issueCoupon` 均按 **产品 ID** 判定，不按金额或标题
- **展示：** 进入兜底时 **始终展示** 优享券卡片；账号尚无可用 `cp_prod_manual` 时调用 `issueCoupon` 新发，已有则复用展示、不重复入库
- **与购票 10 元券区分：** 10 元券（`cp_prod_purchase`）仅在 `single` / `cart` 推荐成功路径推送；5 元优享券仅在 fallback 路径
- **关键文件：** `partyProductMatch.ts`、`purchaseFallbackCoupon.ts`、`TicketFallbackCard.vue`、`TicketsPage.vue`

### 12.3 优惠券逻辑（可闭环路径）

- **主动营销：** `shouldPushPurchaseMarketingCoupon()` — 账号无新客券，或新客券已用/已过期 → 发购票10元券
- **推荐成功展示：** 营销券挂在票卡 `TicketCardPayload.offerCoupon`（可选 `offerCouponHint`），**不再**单独 `unshift` 一条券气泡；同框按 `revealCount` 先券后票
- **追问阶段提前推券：** 仍可为「问人数/日期文案 + 独立券卡」（暂未与问话合并）
- **抵扣计算：** `pickBestCoupon()` — 账号可用券（含刚发的营销券）取最高抵扣；优惠价 = 原价 − 抵扣（购物车按行合计原价）
